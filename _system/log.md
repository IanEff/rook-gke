## 2026-07-07

- **Telemetry rework (Antigravity/Gemini session)**: Ported Sloth from a live in-cluster controller to a build-time model (`scripts/gen_slos.sh` generates `k8s/sloth/prometheus-rules.yaml` from `k8s/sloth/prometheusservicelevels.yaml`, which was trimmed to just `ceph-health` and `ceph-rgw-availability`); rewrote `k8s/topology-catalog/catalog-info.yaml` for GKE nodes (dropped ceph-lab's argocd/cilium/cephfs entities) and authored `k8s/topology-catalog/state-queries.yaml` (PromQL per dependency, consumed by the `whir` resolver); reconciled the raw-block StorageClass onto `pd-balanced`, retiring `storage-class-raw.yaml` in favor of a `kubernetes_storage_class` resource in `rook.tf`.
- **Incident — cluster stuck in ERROR, state/GCP split-brain**: Mid-session, the agent killed a `tofu apply` ~27 minutes in, assuming GKE creation had hung (GKE regularly takes 30+ min in this project). This desynced Tofu state from GCP: `google_compute_network.vpc`/`google_project_service.compute` had to be re-imported (subnet was already saved), and `google_container_cluster.primary` couldn't be imported at all because GKE still held it in an active `CREATE_CLUSTER` operation. Separately, the agent had also read cached checkpoint text claiming the VPC's secondary range names were `pods`/`services` and edited `gke.tf` to match, without checking the range names actually on disk in `vpc.tf` (`gke-pods`/`gke-services`) — breaking the cluster's network references. The agent additionally mutated the read-only `thump` chart (`deploy/chart/thump/values.yaml`) directly instead of overriding at deploy time; this was reverted (`git reset --hard HEAD~2` in that repo, confirmed clean).
- **Resolution (Claude session)**: By the time this session started, the `CREATE_CLUSTER` operation had actually finished (not "still running" as the handover claimed) — the range-name mismatch was also already resolved on disk. The real fault: the cluster's default node pool hit `GCE_STOCKOUT` for `e2-standard-4` in `us-central1-c` (zones `a`/`b` succeeded), leaving the cluster in GCP status `ERROR`, orphaned from Tofu state. Deleted the orphaned cluster via `gcloud container clusters delete`, added `node_locations = ["us-central1-a", "us-central1-b", "us-central1-f"]` to `google_container_cluster.primary` in `gke.tf` to steer future node pools away from the stocked-out zone while preserving the 3-node topology assumed by the topology catalog, then re-ran `tofu apply` from a clean plan (10 to add, 0 to destroy — VPC/subnet were untouched throughout). Also fixed `README.md`/`CLAUDE.md`, which still described the retired live-Sloth-controller and `storage-class-raw.yaml` workflows.
- **Getting Rook-Ceph actually healthy on GKE (same session, continued)**: Once the cluster itself was stable, deploying `rook-ceph` v1.14.7 surfaced four independent GKE-specific blockers to OSDs coming up, each fixed in `rook.tf`/`rbd-module-loader.tf`: (1) GKE's `warden` admission webhook rejects the chart's default `system-node-critical`/`system-cluster-critical` priority classes on mon/osd/mgr and CSI plugin/provisioner pods outside GKE-managed namespaces — overrode to `""`; (2) `cephClusterSpec.monitoring.enabled` needs a *separate* `monitoring.enabled=true` on the operator chart to grant `ServiceMonitor` RBAC, without which `ceph-cluster-controller` reconcile failed before ever reaching OSD setup; (3) the chart's default 1-CPU OSD request saturated `e2-standard-4` nodes once GKE's own DaemonSets and mon/mgr were accounted for — trimmed mon/mgr/osd resource requests; (4) `storageClassDeviceSets` has no anti-affinity by default, so all 3 OSDs first landed on the same node/zone — added `placement`/`preparePlacement` podAntiAffinity to spread one per node. Separately, GKE's current `UBUNTU_CONTAINERD` image ships `rbd.ko` zstd-compressed, which cephcsi's bundled `modprobe` can't decompress (`Exec format error`); added `rbd-module-loader.tf`, a DaemonSet that preloads `rbd` via the host's own `kmod` on every node.
- **Incident — corrupted mon store from live `kubectl delete` of OSDs**: While fixing the anti-affinity issue above, deleted the original (badly-placed) OSD Deployments/PVCs/prepare-jobs directly via `kubectl` instead of Rook's proper purge workflow. This left the OSDMap in an inconsistent state (`FAILED ceph_assert(num_down_in_osds <= num_in_osds)` in `OSDMap::check_health()`), crashing *any* mon that became Paxos leader — not a config issue (confirmed by disabling `mon_osdmap_full_prune_enabled`, which didn't help). **User directive, now standing policy: always destroy-and-rebuild via Tofu, fix the repo not the live cluster — never hand-patch a broken Ceph cluster with kubectl/admin-socket surgery.** Recovery: cleared `ceph.rook.io/disaster-protection` and CR finalizers to unblock `tofu destroy -target=` on the operator/cluster/namespace (Rook's operator can't run its own graceful-cleanup finalizer logic once the cluster it's cleaning up is itself broken), then — critically — wiped `/var/lib/rook` on all 3 GKE nodes via `kubectl debug node` (mon data lives in a hostPath outside Kubernetes' object model entirely, so deleting the namespace/helm releases alone silently left the corrupted rocksdb store in place; the first rebuild attempt resumed the exact same corrupted osdmap epoch `e755` before this was caught). `tofu apply` from a clean plan then bootstrapped a genuinely fresh cluster (fresh fsid, osdmap starting at `e28`/`e29`, `3 total, 3 up, 3 in`, `HEALTH_OK`), with one OSD landing on each of the 3 nodes as intended.
